# Improvement plan for the next closed family pilot

Reviewed commit `e89cd0c` on 23 November 2026. The release target is a provisioned family using a shared tablet and a paired child phone. The first release decision is whether both devices can present the right day, recover from a failed read, and agree about points. Keep the existing React and Supabase architecture. The database already gives the project a single place to enforce family dates, approvals, and balances.

## Implementation and release evidence

The pilot branch now submits the family day from the open task, rejects stale submissions before the point transaction, and refreshes the board at the date boundary and on resume. Guardians and children can retry failed reads. The statement loads older pages in timestamp and ID order. Routine moves announce their saved position. Reward requests account for other pending requests, and the active modal owns keyboard focus. The closed-pilot workflow exercises the production build on a disposable Supabase stack. The recommendations below retain the baseline reasoning and acceptance scenarios.

The first implementation passed the database suite, both development browser journeys, and the closed-pilot browser rehearsal, including re-pairing. Further regression coverage exercises startup retry, family midnight and paginated history. The release checklist covers the remaining hosted and participant evidence. ## A morning the guardian can arrange

In **Rotinas**, a guardian can create **Antes da escola**, assign it to a child on school days, add tasks, then use the up and down arrows to set their order. The outer routine list has its own arrows. Previously, the child saw one three-column grid with two-line labels. The database already returns the routine ID, name, and both ordering fields. The revised Today screen uses that data directly. [Guardian editor](../src/guardian/Routines.tsx) · [Database ordering](../supabase/migrations/20261122000000_child_devices.sql) · [Child board](../src/child/Today.tsx)

| What the child sees in Antes da escola | What happens on tap |
| --- | --- |
| **A seguir · 1. Escovar os dentes** | Opens the picture card. The child can listen to instructions and tap **Fiz!** when finished. |
| **2. Vestir o uniforme** | Available immediately. It becomes the suggestion when the earlier task is done or awaiting approval. |
| **3. Preparar a mochila** | The card can contain the guardian’s illustrated steps, such as opening the bag, adding a notebook, and closing it. One confirmation completes the task. |

Each routine has a heading and an ordered list. Task names wrap, and rows retain their place after completion. Only the earliest actionable task across the day gets **A seguir**. A rejected task returns to its place with the retry message. If all tasks are pending or done, the board has no next suggestion. Dated one-offs appear under **Só hoje** after the routines. The sequence expresses the guardian’s preference. A child who needs to dress before the bathroom is free can open the second task. The feature requires no new schedule fields, per-step points, or migration.

**Checked locally.** At 320 CSS pixels in Edge with reduced motion, a failed first read showed retry and suppressed the empty-day message. After recovery, the built app displayed the named morning routine and a separate one-off group. Opening and confirming task one changed its state to waiting and moved the suggestion to task two. The document fit the viewport. This exercise used fixture responses. The existing full browser scenario now also checks positions in a guardian-created routine. [Scenario](../e2e/main-flow.e2e.ts)

**Next pilot observation.** Ask the guardian to move the backpack task first without coaching. Ask the child “O que você vai fazer primeiro?” and then “E depois?” Observe whether they use the picture, ordinal, heading, or spoken instructions. Repeat with one sibling on a different schedule and an afternoon board full of completed morning tasks. If the child must repeatedly scroll past finished routines to find the suggestion, trial a jump-to-next control that preserves list order and keyboard focus. Record the point of confusion before adding another display mode.

## Before the next family invitation

### 1. Bind a completion to the day the child saw

A child opens a daily task on Monday, leaves the card up, and taps **Fiz!** on Tuesday. The card has a day, but the request sends only child and task IDs. The database resolves Tuesday when processing the request. A recurring task eligible on both days can therefore credit Tuesday from Monday's card. A one-off can instead fail eligibility. A visible, idle tab also has no scheduled family-day refresh. Midnight produces no database change to trigger Realtime. [Product rule](BRIEF.md) · [Child submission](../src/child/ChildApp.tsx) · [Today query](../src/lib/queries.ts) · [Database function](../supabase/migrations/20261122000000_child_devices.sql)

- **Database work.** Add an expected family day to the completion contract in a forward migration. Compare it to the server-calculated day before writing. A mismatch should return a distinct translated outcome and leave both the completion and statement untouched. Update generated types and callers. Coordinate rollout with already-open pilot clients and specify when the legacy signature can be retired.
- **Client work.** Send the day the child confirmed. Refresh day-dependent queries when the family day changes and on resume. Dismiss a stale card, explain the change in Portuguese, and let the child choose today's task. Include the day in the optimistic cache match. Keep the server check even with a client timer because a device can sleep through midnight. Query refetch on focus or reconnect only covers some transitions. [TanStack Query defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)
- **Acceptance.** Against a disposable database, submit yesterday's day for a recurring task valid today. Assert zero new entries, then confirm today's card and assert one credit after a repeated tap. In the browser, cover an open card, a sleeping device, an empty-to-nonempty day, and a device timezone different from the family's. Use a controlled clock or date fixture so CI need not wait for midnight.

### 2. Show families when a read fails

At the reviewed baseline, Today converted missing task data to an empty array. The revised board now waits for a successful read before showing **Nada para hoje!** and offers retry if the first read fails. The statement still displays **Nenhum lançamento ainda.** while its first read is unresolved or failed. The review queue checks pending flags but can still announce an empty queue after an error. A failed profile read can leave the child area blank. These messages can lead a family to skip scheduled work or a guardian to overlook a pending approval. [Child area](../src/child/ChildApp.tsx) · [Today](../src/child/Today.tsx) · [Statement](../src/guardian/Statement.tsx) · [Review queue](../src/guardian/Home.tsx)

- Show a loading state for the first read, a retryable error when it fails, and the empty message only after a successful empty response. Keep existing rows visible during background refresh. If the refresh fails, identify the data as potentially out of date. For the combined queue, keep a successfully loaded section usable while the other retries.
- Cover session startup in the same workstream. A failed family lookup returns the user to loading. A failed initial child-device lookup exits the callback without resolving the session. The existing recovery button reloads the entire page. Give the affected lookup its own retry action and preserve the signed-in identity. Keep transport failures distinct from a successful lookup confirming revocation. [Session resolution](../src/lib/session.tsx) · [Loading screen](../src/App.tsx)
- **Acceptance.** Delay the first response, fail it, then restore it without reloading. Verify the child sees the scheduled task and the guardian sees the pending item. Repeat with successful empty data, cached data, and a revoked device. Only the successful empty response should announce an empty day or queue.

### 3. Exercise the actual closed-pilot configuration

The CI flows create families under the development configuration. Hiding signup in the built client and enforcing the hosted Auth hook are distinct checks. The local config enables signup and leaves the hook example commented. Existing green checks alone cannot establish which settings a deployed pilot uses. [Pilot instructions](family-pilot.md) · [Local configuration](../supabase/config.toml) · [Entry form](../src/entry/Entry.tsx) · [Auth hook migration](../supabase/migrations/20261122010000_pilot_signup.sql)

- Add a separate disposable pilot smoke run with the hook enabled and the production build flag set. Keep the existing open-signup setup test. Exercise a provisioned guardian's first sign-in, closed public registration, child pairing, revocation, and re-pairing. Use fictional identities. Record the client revision and applied migration alongside the result.
- Before invitation, have the pilot operator repeat the normal journey on the intended deployment. Document who can restore a guardian account and issue a fresh child link when browser storage is cleared. Supabase anonymous identities depend on the device's stored session. [Supabase anonymous sign-ins](https://supabase.com/docs/guides/auth/auth-anonymous)
- **Acceptance.** The provisioned guardian completes setup, public family registration is declined, pairing succeeds, and revoking one child device preserves the other device's link. Retain the result with the release record.

### 4. Verify the interaction on the family's hardware

Exercise the pilot's QR and Home Screen instructions on an iPhone and the shared-device flow on the intended tablet. Use the normal motion setting as well as reduced motion. During a guardian approval, leave a card open while the day celebration appears. Each mounted modal currently installs its own document key handler, and the portals sit outside the inert app root. That makes overlapping dialogs a specific keyboard risk to verify. [Modal implementation](../src/child/CardDialog.tsx) · [Celebration](../src/child/Celebration.tsx) · [WAI modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

- **Acceptance.** Tab and Shift+Tab stay inside the active dialog. Escape dismisses one layer and restores focus. Read-aloud speaks the selected Portuguese task, confirmation survives a double tap without duplicate credit, the phone reopens in the paired profile, and a guardian sees the result from the other device.
- During the first supervised session, observe whether the child distinguishes pending approval from earned points. Record the screen, action, device, and observed confusion using fictional task names. Prioritize any failure that prevents an unaided completion or misrepresents the balance.

## Delivery order and release decision

Land the date-contract regression and fix together, then the read-state and retry changes. The disposable pilot smoke run can proceed independently. Run the physical-device rehearsal against the resulting release candidate. Invite the next family once the daily task posts to the intended day, failed reads recover visibly, and pairing, revocation, and point reconciliation pass on the intended deployment. A failure should identify a screen, device, expected result, and observed result so the next change has a repeatable check.

The existing architecture decisions already cover family login, guardian PINs, the web client, Supabase, and paired devices. Revisit an ADR if the pilot changes one of those commitments. The immediate fixes implement rules already in the product brief.
