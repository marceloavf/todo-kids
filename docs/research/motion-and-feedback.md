# Motion and feedback

Feedback should tell a child what changed. Marking a task that needs approval means “waiting”; it cannot promise points. Submitting a reward request likewise leaves the balance intact. Reserve stronger feedback for a confirmed outcome.

| Event | Intended response |
| --- | --- |
| Open a task | Show its picture and instructions; delay confirmation briefly to avoid accidental double taps. |
| Finish an immediately credited task | Mark it done and connect the earned points visually to the balance. |
| Submit a task for review | Show a steady waiting indicator. |
| Receive guardian approval | Show a short notice with the outcome. Avoid replaying old decisions after reopening. |
| Complete the day | Show one dismissible celebration, including when the last approval completes the day. |
| Request or receive a reward | Distinguish a pending request from confirmation and spending. |

Use the child's sound, read-aloud and reduced-motion settings. Respect the operating system's motion preference. Stop effects on leaving the screen. For device testing, check rapid taps, a low-powered phone, silent mode and whether the task still makes sense with movement disabled. The prototype observations and animation timings were design inputs; timing alone cannot establish usability.

Sources: [UNICEF design toolbox](https://www.unicef.org/childrightsandbusiness/workstreams/responsible-technology/online-gaming/ritec-design-toolbox), [Apple motion guidance](https://developer.apple.com/design/human-interface-guidelines/motion), [original specifications, benchmarks and evidence notes](https://github.com/marceloavf/todo-kids/blob/f854579/docs/research/gamificacao-e-animacoes.md).
